How Gatekeeper works today

A multi-tenant API gateway platform. Administrators define tenants and their routes in a control plane; a data-plane gateway is meant to serve them. This page shows the current flow of the project, what is built, and what is still a scaffold.

Architecture

Solid arrows exist in code and work today. Dashed arrows and dashed boxes are the intended design: the pieces are declared but not connected.

Three roles, three areas

Each account has one role. The role decides which API prefix works and which part of the UI opens after sign-in.

Platform admin

PLATFORM_ADMIN

API: /api/platform/**

Creates organizations (tenants), sets their status, and manages each organization's tenant administrator.

UI: /platform/organizations

Tenant admin

TENANT_ADMIN

API: /api/tenant/**

Manages the routes, header rules, version history and audit log of their own organization, and can rename it.

UI: /tenant

Gateway service

GATEWAY_SERVICE

API: /api/gateway/**

Reads the list of all active routes of all active organizations. The data plane is meant to poll this.

UI: /gateway

Tenant isolation: the organization comes from the organizationId claim in the signed JWT, never from the URL or body. It must be ACTIVE on every request.

Step-by-step flows

Pick a scenario. Each step shows who acts, what they do, the API call, and what the backend does.

  1. Platform admin
    Signs in
    POST /api/auth/login
    Receives a JWT with role PLATFORM_ADMIN and no organization.
  2. Platform admin
    Creates the organization (name and slug)
    POST /api/platform/organizations
    Row saved with status PENDING. Audit: CREATE_ORGANIZATION.
  3. Platform admin
    Creates the tenant administrator
    POST /api/platform/organizations/{id}/tenant-admin
    User saved with role TENANT_ADMIN and a BCrypt password hash. One per organization.
  4. Platform admin
    Sets the organization to ACTIVE
    PATCH /api/platform/organizations/{id}/status
    Required before the tenant can sign in.
  5. Tenant admin
    Signs in
    POST /api/auth/login
    Token now includes the organizationId claim. Lands on the tenant dashboard.
  1. Tenant admin
    Opens Routes and chooses Create route
    GET /api/tenant/organization
    The UI reads the organization slug to pre-fill the path pattern as /<slug>/.
  2. Tenant admin
    Fills the form and saves
    POST /api/tenant/routes
    Backend checks the path prefix, target URL, header rules and duplicate route ID, then saves the route as version 1, inactive, plus a CREATED snapshot and an audit record, in one transaction.
  3. Tenant admin
    Activates the route
    PATCH /api/tenant/routes/{id}/status {"active": true}
    Version 2, snapshot ACTIVATED, audit ACTIVATE_ROUTE.
  4. Tenant admin
    Edits the route later
    PUT /api/tenant/routes/{id}
    Whole route replaced, header rules rebuilt, version incremented, UPDATED snapshot stored.
  5. Tenant admin
    Reviews history
    GET /api/tenant/route-versions/{routeId}
    Version cards newest first; each can show the exact JSON snapshot.
  1. Gateway
    Signs in with the gateway-service account
    POST /api/auth/login
    Token with role GATEWAY_SERVICE. (The gateway service does not do this yet.)
  2. Gateway
    Fetches the route feed
    GET /api/gateway/routes
    Returns every route where active = true and the owning organization is ACTIVE, each tagged with organizationId.
  3. Gateway (intended)
    Builds its routing table
    —
    Match pathPattern, allow listed methods, apply header rules, rate limit, forward to targetBaseUrl + targetPathPrefix.
  4. Gateway account in the UI
    Inspects the same feed
    /gateway/routes
    The Active routes page is a read-only, searchable view of exactly this response.
  1. Platform admin
    Sets the organization to SUSPENDED
    PATCH /api/platform/organizations/{id}/status
    Audit: CHANGE_ORGANIZATION_STATUS. No data is removed.
  2. Gateway
    Next feed fetch
    GET /api/gateway/routes
    The tenant's routes are no longer returned.
  3. Tenant admin
    Uses an existing token
    any /api/tenant/**
    Refused: "The organization is not active", even though the token has not expired.
  4. Platform admin
    Sets it back to ACTIVE
    PATCH .../status
    Everything works again; routes are served again.

Route lifecycle and versioning

Every change to a route bumps configurationVersion and stores a full JSON snapshot. History is keyed by the business route ID, so it survives deletion.

v1Createinactive · CREATED
v2Activateserved by gateway · ACTIVATED
v3Editsettings or header rules · UPDATED
v4Deactivatenot served · DEACTIVATED
v5Deletefinal snapshot kept · DELETED

Things to know before relying on it

High

Business errors surface as HTTP 500

No @ControllerAdvice exists, so ApiException (401, 403, 404, 409) is likely returned as a generic 500.

Medium

Seeded accounts and early secrets

Secrets now come from a git-ignored .env, but the seeded platform-admin and gateway-service hashes are committed in V3. Change those passwords and use a fresh JWT secret when deploying.

High

Gateway and analytics cannot validate tokens

No resource-server or decoder is configured in those two services.

Medium

Re-creating a deleted route ID fails

Version history is unique per route ID and version, and a new route restarts at version 1.

Medium

No pagination, no token revocation

All lists return everything; a disabled user's token works until it expires.

Note

Platform actions show in tenant audit logs

Operations on an organization are recorded against it, so its tenant sees them.
